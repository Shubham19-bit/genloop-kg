2. Methodology

Data. 35 large US companies in 4 sectors (9 tech, 9 financials, 9 consumer, 8 healthcare) so sector-level comparisons are possible. For each, the latest 10-K whose fiscal period ended between 2025-05-01 and 2026-02-28 (one comparable year despite different fiscal year-ends; the exact period end is stored on every fact). EDGAR serves 10-Ks as HTML, so each was printed to PDF with headless Chromium; Wells Fargo's statements live in Exhibit 13, which was merged into its PDF. Everything downstream reads only the PDFs.

Graph. A property graph (NetworkX, 1,126 nodes, 2,784 edges). Facts are nodes, not edges: Company → Fact{value, unit, scale, period, evidence row} → Metric, Fact → Period, Fact → Page ← Filing, so every answer carries its source page. A metric dictionary maps 60+ surface labels ("Total net sales", "Total revenue, net of interest expense", "Sales to customers"…) to 12 canonical metrics, which is what makes cross-company comparison possible. Shared entity nodes (Auditor, City→State, Sector, Person, Segment) connect the 35 filings for multi-hop questions. Ratios (margins, debt/equity, ROA, R&D intensity) are computed at query time and cite both input facts.

Extraction. Numbers (382 facts): rule-based, no LLM. Words are regrouped into table rows by position; primary statement pages are found by their title; the current-year column is read from the header; scale ("in millions") is applied; labels are matched against the dictionary in priority order (totals before sub-lines). Liabilities are derived as assets − equity only where no line exists, and are flagged as derived. Auditor and employee count also come from regex (34/35 and 30/35 found). Text facts (HQ, CEO, incorporation, segments) come from a local LLM (Qwen 3.5 9B via Ollama) given only 2–3 candidate pages. It must return an exact quote and page, and the code rejects any fact whose quote is not on that page.

Query. The LLM never answers. It converts the question into a small JSON plan over 8 operations (companies, metric, ratio, rank, filter, aggregate, diff, attribute), with a prompt generated from the graph's own schema. Python then executes the plan as graph traversals and returns the answer, the fact keys it touched and their pages. If a fact is missing it returns "no answer" rather than guessing.

Benchmark. 30 questions (10 single-fact, 10 multi-hop, 10 comparison), written before any QA run and covering every metric and relation type. Question wording was drafted with an AI assistant and then edited by me. Gold values were located with a different model from the pipeline's (Gemini chat) using a fixed written rubric, one PDF at a time. Every gold number was then checked against the filing's inline-XBRL tag (334/335 agree), and text facts were checked on their quoted page. Winners, sums and ratios were computed in code from the verified values. Each question lists all the facts needed to justify its answer: for "highest X in sector S", that is X for every company in S plus any final hop. Two questions were rewritten before the first run because their gold facts don't exist (Amazon has no total-liabilities line; Morgan Stanley has no long-term-debt line). Scoring: numbers within 1%, ratios within 0.05 percentage points, entities by alias match, text by key name.

What changed after the first run. Three executor fixes and one extraction fix: (1) accept plan forms the planner naturally produced (a ratio of two earlier steps; diff over two steps); (2) one bad plan fails only its own question instead of the whole run; (3) the audit-signature search now covers multi-page reports, raising auditor coverage from 23 to 34 of 35; (4) US state abbreviations are normalised ("Purchase, NY" → New York).

3. Gaps: where and why it failed

  • Q18, a silent wrong total (most important). "Combined revenue of companies headquartered in New York state": the LLM never extracted Pfizer's HQ, so the filter matched 7 of 8 companies. The system returned $595.5B instead of $658.1B with no warning. Missing coverage turned into a confident wrong number, which is unacceptable for a bank.
  • Q10, regex vocabulary. Goldman reports a "headcount of 47,400"; the employee pattern expects "employees". The system said "no answer". That is the right behaviour, but the fact is lost. 5 of 35 employee counts are missing for similar reasons.
  • Q24, planner invented syntax ("input": [{"ref": "s2"}]) that isn't in the plan language. Execution was rejected, so the question failed safely with no wrong answer.
  • Q19, correct but imprecise. The planner read "bank" as 6 banks (dropping Visa, Mastercard and AmEx from the Financials sector) and added an unneeded "incorporated in" hop. Recall was 0.73 and precision 0.89. The answer was still right only because JPMorgan wins either way.
  • LLM extraction errors outside the benchmark. The exact-quote check caught a hallucination: JPMorgan's segments included "Commercial Banking", which isn't on the page, so it was rejected. It did not catch Morgan Stanley's CFO being listed as a second "CEO", because her name is on the signature page. Two HQs (Pfizer, Target) are missing. Bank of America's auditor signature is an image.
  • Comparability limits. Fiscal years end in different months (May 2025 to Feb 2026), definitions differ (bank "cash", "long-term debt" vs "borrowings"), and pharma and bank income statements have no operating-income line. These are stored and reported, not hidden.
  • Benchmark limits. 30 questions written by the system's designer, mostly numeric, and with no unanswerable questions. That probably flatters the system.

4. Improvements with more time

  • Coverage-aware answers. Before an aggregate or ranking, check that the filter relation exists for every candidate company. Otherwise answer "partial: k of n companies have this fact". This would have turned Q18 into a flagged answer.
  • Plan validation: a JSON schema for plans, with one retry that feeds the validation error back to the planner (fixes Q24-type failures).
  • Two-source extraction: run regex and the LLM for each text fact and keep only agreeing values (or flag disagreements). Use XBRL at ingestion as a validation layer, still not as an answer source.
  • More context: multi-year facts and 10-Qs (the schema already has Period nodes), notes such as debt maturities and segment revenue, and links from each fact to the MD&A paragraph that explains it, so "why did X change?" can be answered from the graph with citations.
  • A harder, independent benchmark: written by someone who hasn't seen the schema, with unanswerable and ambiguous questions to measure abstention.
